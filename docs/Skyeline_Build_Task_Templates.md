# Skyeline Build Task Templates

These templates auto-populate when a new project of the matching type is created in Skyeline OS. The wizard's project-type selection determines which template seeds the project's `tasks` collection; the GC can then adjust the dates, swap assignees, or add custom tasks from the Tasks page. Days are offsets from the project's start date — the system computes the actual calendar dates when the template is applied.

## Notes

**The Assignee column shows the ROLE, not a specific person.** Actual humans get filled in when the template is applied to a project — Skyeline OS reads the project's team assignments (GC, designer, project manager, awarded subs per trade) and resolves each role to the right person via `client/src/lib/taskDefaults.ts`. The same template applied to two different projects produces two different assignee sets without any template edits.

**Categories map to the phases used elsewhere in the app** — Pre-Build, Site Work, Foundation, Framing, Exterior, MEP, Insulation, Drywall, Paint, Cabinets, Countertops, Tile, Trim, Flooring, Pool, Glass, Closeout. The kanban-by-category view on the Tasks page groups by these categories, and the Selections Manager uses the same category names so tasks and selections stay aligned per phase.

**This document is generated from `client/src/lib/starterJobTemplates.ts` — that file is the source of truth.** Edits to task content, durations, or assignee roles should happen in the TypeScript file (which gets deployed with the app), and this Markdown should be regenerated to match. Out-of-band edits to this doc will be overwritten on the next regeneration.

**Seed behavior** — `seedStarterJobTemplates()` in the same file writes each template to Firestore's `templates` collection on first run, with each task as a doc in the `templates/{id}/jobTasks` subcollection. The seeding is idempotent: templates matched by name are skipped on re-runs, so you can safely call it multiple times.
